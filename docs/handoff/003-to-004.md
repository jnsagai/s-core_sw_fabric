# Handoff: increment 003 to increment 004

Increment 003 now derives a deterministic, closed workflow package from a complete sealed 002 plan
and a reviewed execution mapping. Increment 004 may build native artifacts and traceability over
the retained obligation identities and source origins. It must not use Fabro run state or generated
workflow text as authority for native S-CORE artifacts.

## Available inputs for 004

- The sealed 002 plan binding in the package manifest, including exact semantic digest.
- Stable plan instance IDs retained on each typed action node and gate obligation.
- Full node and edge logical keys plus content-addressed IDs.
- Source-map entries covering nodes, edges, gates, loop policies, fan groups, native files, and
  material renderer decisions.
- Explicit action inputs, expected outputs, allowed paths, data destinations, write scope, role,
  tool profile, model-capability binding, finite budgets, completion predicate, evidence
  expectation, outcomes, and prohibited authority.
- A canonical native source set and exact compiler/validator/input baseline vector that can be
  compared without Fabro.

## 004 prerequisites and constraints

1. Revalidate the workflow package self-digest, per-file digests, source-map coverage, compiler
   profile, validator profile, and selected plan/mapping digests before deriving artifacts.
2. Preserve native S-CORE schema names, IDs, statuses, references, and containment relationships;
   do not translate workflow node IDs into native artifact IDs.
3. Treat `expected_outputs` and data destinations as declared obligations and boundaries, not
   evidence that an artifact exists or is acceptable.
4. Keep artifact generation deterministic and source-cited. Every generated document wrapper and
   contained need must retain its native source and plan-instance relationship.
5. Reject missing expected obligations and allocation coverage; validating only links already
   present is insufficient.
6. Keep direct edits to generated artifacts distinguishable from reviewed source/profile changes.
7. Do not authenticate approvals, accept evidence, promote readiness, register/run workflows, call
   models/providers, or mutate production targets in 004.
8. Maintain the package boundary values `registration`, `execution`, `evidence`, `acceptance`,
   `engineering_readiness`, and `release` as `not_evaluated` unless their owning increments supply
   verified state.

## Known unresolved inputs

The production execution mapping remains pending owner review. The real native tests use synthetic
fixture review records and prove compiler/validator behavior only. The upstream security-FDR ID
conflict, protected decision verification, supported production Fabro selection, and existing
human review checklists remain unresolved. Increment 004 should use fixture packages for contract
development until the corresponding owner decisions are available.

Next step: specify increment 004 native-artifact and traceability contracts around exact native
schemas, expected obligation coverage, wrapper/need validation, and package-source binding.

Recommended model: `gpt-6-sol` with `xhigh` reasoning, because 004 requires careful native-schema
preservation, bidirectional traceability, and adversarial missing-obligation tests across several
source contracts.
