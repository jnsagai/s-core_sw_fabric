# s-core_sw_fabric Constitution

## Core Principles

### I. Native authority
S-CORE's pinned process and accepted project tailoring MUST define target engineering
semantics. Spec Kit MUST govern only development of this integration.

### II. Portable engineering record
Native artifacts, review history and verification evidence MUST remain intelligible
and independently checkable without Fabro. Incomplete records remain incomplete.

### III. Explicit execution policy
Every gate, omission and mapping MUST cite upstream process, project configuration
or an authorized human decision. LLM interpretation MUST NOT silently become policy.

### IV. Human accountability
Required engineering judgments MUST bind authorized people, roles, independence,
exact subjects and authenticated origins. AI critics MUST NOT substitute for people.

### V. Deterministic acceptance checks
Versioned deterministic tools MUST evaluate structural and measured predicates.
Semantic adequacy MUST retain the required engineering reviews. Tools are not
qualified merely because they are deterministic.

### VI. Fail-closed readiness
Missing, unknown, stale, unsupported or untrusted mandatory evidence MUST block the
affected acceptance. Passing tests or a successful runtime MUST NOT imply readiness.

### VII. Traceable changes
Changes MUST connect intent, native artifacts, implementation, verification and
review subjects. Impact MUST include transitive and newly introduced dependencies.

### VIII. One runtime
Fabro MUST own execution, scheduling, events, checkpoints and run state. Derived
indexes MUST be rebuildable; no competing scheduler or requirements store is allowed.

### IX. Bounded AI execution
Agents MUST have explicit paths, tools, model capabilities, data destinations,
budgets and retry limits. They MUST lack trusted collector and approval credentials.
Required human gates MUST stop unattended runs.

### X. Incremental delivery
The fabric MUST use bounded Spec Kit specifications, plans and tasks. Stable FAB IDs
MUST remain traceable. Later increments MUST NOT be claimed by an early demonstration.

### XI. Truthful evidence
Real tool execution, human decisions, imported verified evidence, fixture replay
and agent assertions MUST remain distinguishable. Agents MUST NOT self-attest results.

### XII. Reproducibility and provenance
Compatible source/tool pins, license notices and reproducible commands MUST accompany
evidence. Reference repositories MUST remain read-only; generated builds use disposable copies.

### XIII. Deterministic context minimization
Deterministic tools MUST narrow impact, classify tasks and select baseline-bound context
before model invocation. Complete evidence MUST remain outside conversational context;
agent tools MUST return bounded summaries and exact artifact references. Every stage MUST
have per-result and aggregate limits. Missing dependencies MUST widen scope or block it.

### XIV. Lazy procedural guidance
Skills MUST describe one activity, load only when selected and bind their version and
content digest to context. Skills MUST NOT establish engineering authority, applicability,
freshness, trust or acceptance. Runtime Skill availability MUST be explicitly rendered
or retrieved; a Codex Skill installation MUST NOT imply Fabro runtime support.

### XV. Measured operational limits
Operational budgets MUST narrow absolute role/model ceilings. Escalation and critique
MUST follow explicit deterministic triggers. Unknown provider usage MUST remain unknown
and block uncontrolled continuation. Repeated failures or absent progress MUST stop bounded
loops. Optimization claims MUST identify measurements, estimates and unmeasured limits;
required verification and human gates MUST NOT be reduced for token savings.

## Execution Boundaries

AI drafts and implements within explicit permissions. APM/MCP supplies supported
context/tools. Native target repositories own engineering content. Publication,
merging, release and deployment are separate actions requiring their own authority.
C++17 and MISRA C++:2023 are the initial target policy, not Python coding rules or a
claim of compliance. Language, reliability and release profiles need explicit support.

## Development Workflow

Each increment MUST have a bounded spec/plan/tasks, requirement mapping and actual
acceptance evidence. Research MUST precede adapter design. Clarification and
consistency findings MUST be recorded. Required human reviews remain unchecked until
performed. The first session ends at the 000-to-001 handoff; 001 is planned only.

## Governance

This initial 1.0.0 proposal implements the owner's supplied principles; owner review
is pending, with no independent ratification claimed. Amendments MUST record rationale,
impact on specifications/contracts/gates and reviewer decision. Use major versions for
incompatible principle changes, minor for new obligations, patch for clarifications.
Implementation reviews MUST check these boundaries and record justified exceptions.
